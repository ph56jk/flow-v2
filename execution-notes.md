# Execution notes — HaviGroup ERP migration

## Scope and safety decisions

- ERP access is locked to Project `PROJ-0049` and uses the documented HTTPS GraphQL endpoint only.
- Credentials are local-only (`ERP_API_KEY` and `ERP_API_SECRET`) and are never returned to the browser, exported, logged, or committed.
- Flow v2 reads image source URLs from an ERP Task. It does not send ERP credentials when retrieving those public HTTPS assets.
- Dashboard approval is mandatory. Only fully approved artifacts with public HTTPS URLs are appended to the source Task via the GraphQL `addTaskComment` mutation.
- The integration never creates, resets, or deletes ERP Tasks. It writes in exactly three ways, all confined to the configured project: comments/attachments on a Task, `updateTaskStatus` on the target card (`Pending Review` when review images are posted, `Completed` when approved images land), and `hvg_workspace.api.delete_task_comment` to pull back a single review comment whose image a human rejected with 👎.
- Status moves are best effort and one-way through the review flow: a card already `Completed` or `Cancelled` is never touched, and a card whose images were all rejected is never advanced.
- Rejections made by the tool itself (the watermark gate) never delete an ERP comment — only a human 👎 from the dashboard, an ERP reply, or Telegram does, so `reopen_watermark_rejections` still works.
- The bytes that leave for ERP are cleaned twice. The 2K upsample round-trips the picture through Google, which re-stamps the Gemini sparkle onto the result, so every outgoing file goes through removelogo again before upload, with `watermark_repair` as the fallback. The local measurement is not a gate on that call: on wood grain and linen it reads 0.10–0.24, under `MIN_STRENGTH`, while the sparkle is plainly visible, so gating on it shipped whole cards marked.
- The 2K pass for a whole batch runs inside one `_with_client` session (`_upsample_artifacts_bytes`). Each call to `_with_client` opens and validates a Flow project page; paying that per image made the upload step roughly three quarters of a twelve-image run's wall clock, on top of the generation it was uploading.
- That batch passes `hold_session_lock=False`, so `_with_client` gives the browser session lock back the moment the client exists. The five and a half minutes it then spends are `POST flow/upsampleImage` through `client._api`, which is plain HTTPS over the browser's request context and touches the page only to read a cached bearer token — nothing another card's generation can trip over. Without this the second idea card queued behind the first one's upscales, which is most of a card.
- The one part of that path that does drive the page is `_upsample_image_via_flow_ui_download`, the last-resort fallback. It takes `_browser_session_lock` back (and `_flow_upsample_ui_lock` after it, never before — a caller holding the session lock takes the UI lock next, so the reverse order would deadlock the pair).
- Idea cards fan out two at a time (`_erp_idea_concurrency`, env `ERP_IDEA_CONCURRENCY`). The browser stays single-file — `_with_client` still holds `_browser_session_lock` through any call that drives the page, so no two cards can be inside the Flow Agent panel together — and what overlaps is the 2K batch, the watermark pass and the ERP uploads, during which the browser used to sit idle.
- Generation in Agent mode pays a fixed dead wait: the app waits up to 45s for a successful `batchGenerateImages` response that the Agent panel does not produce, times out, then finds the images by polling the project ~10s later. Measured on three live cards, every one of them took the timeout and then succeeded through the poll. That is ~45s per idea, so `_flow_agent_network_wait_seconds` (env `FLOW_AGENT_NETWORK_WAIT_SECONDS`, default `45`) exists to shorten and re-measure it without a code change. Measured at `15`: the wait timed out at 15.0s exactly as set, the project poll then found the image ~9s later, and the image came out clean and 2K — 30s saved with no loss. One sample, so the default stays `45` and the shortened value lives in `.env.local`. Note the two runs still finished within four seconds of each other (148s vs 152s): a different step, waiting for the Agent approval dialog, varied by 26s between them and swallowed the gain. That wait is the next thing worth measuring.
- What the batch must not overlap is another card's batch, so they take turns on `_flow_upsample_batch_lock` (taken outside `_with_client`, before the session lock). Letting two cards upscale together measured 87–105s an image against 31s for a batch running alone, and 5 of one card's 12 images came back un-upscaled. The browser is still handed back, so the next card's generation overlaps — that is the part that pays; the queue is not.
- Every un-upscaled image on the live cards was one error: `HTTP 403 on upsampleImage: reCAPTCHA evaluation failed`. Not throttling and not an aged media id — the logs show the same media upscaling fine on a later attempt. Two things caused it. The token is minted by `_client_context`, which runs `grecaptcha.enterprise.execute` through `page.evaluate` and reloads the page when the first read comes back empty; the batch had already handed the browser session back, so it was evaluating on whatever page the next card was generating in. `_flow_upsample_client_context` now takes `_browser_session_lock` for the mint alone (and only when the caller let go of it — taking a lock it already holds would hang), leaving the upscale itself outside, which is the part worth overlapping. And a refused token used to be final: one token, one chance, image stays 1024 forever. `_upsample_image_via_flow` now runs in rounds (`_flow_upsample_recaptcha_rounds`, env `FLOW_UPSAMPLE_RECAPTCHA_ROUNDS`, default `3`), minting a fresh token per round, and only retries when the failure was the token — anything else fails identically with a new one.
- Measured after the fix went live: the retry rounds fire, and Google refuses all three — a fresh token is turned down exactly like the stale one, twice in a row on two separate single-image runs. So the retry is not what saves the image; `_upsample_image_via_flow_ui_download` is, and it does not log on success, which is why the path is easy to miss. The earlier 1024px images were the case where *both* failed: API 403, then `Flow UI 2K download skipped: media tile not found`. What the rounds still buy is the genuinely raced token. **Correction (this sentence used to name two symbols that no longer exist):** `_flow_upsample_rounds_for_next_image` and `FLOW_UPSAMPLE_RECAPTCHA_GIVE_UP_AFTER` were added in 04b6ee2 and removed again in 17d860a. What replaced them is better and is durable per media, not per run: `FLOW_UPSAMPLE_RECAPTCHA_RESULT_KEY`, the `FLOW_UPSAMPLE_RECAPTCHA_MANUAL_AFTER_DEFAULT` threshold, a 24h cooldown and the `needs_manual_review` flag. The per-run cheap-out counter added later is a *different* mechanism and carries a different name on purpose — `FLOW_UPSAMPLE_RECAPTCHA_RUN_GIVE_UP_AFTER`. A successful API upscale still hands the retries straight back, and now resets both records. Still open: why the token is refused at all. `_compat_get_recaptcha_token` mints with `action: 'GENERATE'`, which is the generation action, not an upscale one; worth capturing what the Flow page itself sends when a human clicks 2K.
- An image that missed 2K cannot be fixed after the fact: Flow answers a re-upscale of an old media id with the original bytes. The only route is to delete the review comment and generate a new image. Beware `erp-review/publish` as a repair tool — it posts every artifact index that has no comment on the card, so it refills slots deleted long ago; one call meant to replace a single image posted six and took the card from 12 attachments to 17.
- Sending several 2K upscales at once was tried and reverted (`_flow_upsample_concurrency` default `1`). Four in flight measured 40–50s an image against 27.5s one at a time on live twelve-image cards, and 4 of 24 images came back un-upscaled against 0 in the sequential run — Google appears to queue them per account. The knob remains so the measurement can be repeated.

- The Agent quota block was held for a flat 24 hours, which is longer than the quota's own cycle and cost most of a working day. Measured 18-19/08: Flow refused at 05:36 PT on the 18th, the app blocked `Flow profile 1` until 05:36 PT on the 19th, and a hand-run at 01:00 PT on the 19th generated twelve clean images immediately — so Google had handed the quota back at midnight PT and the app was the only thing still saying no. `_flow_profile_block_seconds` now blocks to the next midnight in `America/Los_Angeles` with a 30-minute floor (`FLOW_QUOTA_MIN_BLOCK_S`) in case Google is late; `FLOW_CHROME_PROFILE_QUOTA_BLOCK_S` still pins it by hand.
- While every profile was blocked, the watcher and the agent bot each kept fanning out anyway — one job per child card, every three minutes, each dying in about five seconds at the browser step. Six cards filled all 50 history slots by mid-morning and pushed the real history out of the dashboard, which is what made the failure look like "nothing runs" instead of "quota". `_flow_quota_pause_reason` now holds the whole round off while every profile is blocked; the repair pass still runs first, because re-posting images that already exist needs no Flow. Marking a profile blocked also logs the profile, the unblock time and the reason — previously it logged nothing at all, so the log for that morning had no trace of the cause.
